Released in mneme-hq 0.9.0: a local stdio MCP server with exactly six Decision Index tools. It can read decisions and record non-authoritative proposals. Human decision authority and deterministic protection remain separate surfaces.
Operator reference · mneme-hq 0.9.0

Decision context over MCP, with authority kept outside the protocol.

Use mneme decision-mcp to let an MCP host query Mneme's Decision Index or submit candidate architectural decisions. The server is local and stdio-only in 0.9.0.

By Theo Valmis·Published September 2026

Install and run

The MCP SDK is an optional dependency. Install the released package with the extra, then start the server from the repository whose decision state you want to expose.

pipx install "mneme-hq[mcp]==0.9.0"
mneme decision-mcp

The process communicates over standard input and standard output. Version 0.9.0 does not expose HTTP, SSE, a hosted endpoint, authentication, RBAC, or multi-tenant infrastructure.

OptionBehavior in 0.9.0
--proposals <path>Use a specific decision-proposals JSON file. When omitted, the durable default is .mneme/decision_proposals.json. Passing an empty string explicitly selects an in-memory proposal store.
--adr-dir <path>Compile that ADR directory into the server's canonical read index. There is no default. The directory must pass parse, corpus validation, and precedence resolution before startup.
 
mneme decision-mcp \
  --proposals .mneme/decision_proposals.json \
  --adr-dir docs/adr

Strict startup: a missing or empty --adr-dir, malformed ADR, invalid corpus, or unresolved precedence prevents the configured canonical server from starting. Mneme does not silently serve an ambiguous canonical view.

Configure an MCP host

Version 0.9.0 ships the server command, not a client-specific installer or generated config. For an MCP host that supports launching a local stdio process, use this process definition in the host's own MCP configuration format:

{
  "mcpServers": {
    "mneme": {
      "command": "mneme",
      "args": [
        "decision-mcp",
        "--proposals", ".mneme/decision_proposals.json"
      ]
    }
  }
}

Add "--adr-dir", "docs/adr" only when that directory is a schema-valid Mneme ADR corpus. MCP host configuration formats differ; this is the process contract, not a claim of validated support for a named client.

Storage and canonical input

The proposal store is always composed. By default it is the local file .mneme/decision_proposals.json; writes are handled by Mneme's JSON proposal store. It is separate from .mneme/project_memory.json, which the MCP server never uses as proposal storage.

Canonical reads are optional. Supplying --adr-dir builds an in-memory canonical index through Mneme's existing ADR compiler. Omitting it starts a proposal-store-only server: proposal tools work, while no ADR-backed canonical decision corpus is loaded.

The frozen six-tool surface

The tool inventory is part of the authority boundary. Version 0.9.0 registers exactly these six names and no aliases.

decision.proposeWrite · proposal only
Purpose
Submit one candidate architectural decision. Identical source, version, and content submissions are idempotent.
Inputs
candidate with required non-empty title and statement; optional rationale, scope hints, architecture context, related decision IDs, and source provenance. A usable proposal requires provenance: producer name/type and source reference, with optional external ID, source version, repository locator, and origin classification.
Result
created, reused, and a proposal record containing proposal_id, proposal_status, candidate content, provenance, fingerprints, proposed time, and any accepted decision link.
Errors
Malformed or missing provenance, empty required text, unknown fields, or forbidden authority fields return a tool error.
Boundary
Creates or reuses only a proposed record. It cannot accept it, create a canonical decision, add rules, or change enforcement.
decision.propose_batchWrite · proposal only
Purpose
Submit multiple independent candidates from one producer output while preserving input order.
Inputs
Non-empty candidates list and optional shared_provenance. Candidate-level provenance takes precedence where supplied; every candidate must resolve to provenance.
Result
results contains one ordered propose result per candidate, each with its own proposal identity and created/reused outcome.
Errors
Empty batches, unresolved provenance, malformed candidates, or forbidden fields fail the call.
Boundary
No batch acceptance exists. Every returned proposal remains independently reviewable and non-authoritative.
decision.getRead only
Purpose
Retrieve one proposal or loaded canonical decision by stable ID.
Inputs
Non-empty record_id.
Result
An explicit record_type of proposal, canonical_decision, or not_found. Proposal and canonical lifecycle vocabularies remain separate.
Errors
Malformed input is a tool error. An unknown ID is successful typed data, not an error.
Boundary
Never mutates proposal, canonical, rule, evidence, or enforcement state.
decision.searchRead only
Purpose
Run deterministic text and exact-metadata search across proposals and the loaded canonical index.
Inputs
Optional text query; proposal status; canonical lifecycle status; producer name; source reference; and origin classification.
Result
Separate proposals and canonical_decisions lists. Search ranking has no enforcement meaning.
Errors
Invalid lifecycle or origin vocabularies and malformed fields return a tool error.
Boundary
Retrieval only. Search cannot decide applicability for a typed rule or grant authority.
decision.applicable_toRead only
Purpose
Find proposal scope hints and canonical context scopes that overlap supplied context or paths.
Inputs
Optional context and paths string lists.
Result
proposal_hint_matches plus slim canonical_scope_matches containing identity, statement, lifecycle, and context scope.
Errors
Malformed argument types return a tool error.
Boundary
Scope hints are retrieval context, not rule applicability. Paths are not glob-evaluated, and the result contains no rules or enforcement state.
decision.traceRead only · fail closed
Purpose
Return the lineage actually known for a proposal or loaded canonical decision.
Inputs
Non-empty record_id.
Result
Explicit result_type: proposal_trace, canonical_trace, or trace_not_found. Missing links are named rather than invented.
Errors
Malformed input is a tool error. Canonical rule-lineage integrity failure aborts the call with JSON-RPC internal error -32603; no partial trace is returned.
Boundary
Trace reports proposal, canonical, rule, and declared-evidence links where they exist. It cannot create or repair any link.

Errors and fail-closed behavior

  • Unknown IDs are returned as typed not_found or trace_not_found results.
  • Invalid inputs return MCP tool errors so the caller can correct the request.
  • Authority-shaped input such as producer-supplied status, proposal IDs, timestamps, canonical lifecycle, typed rules, trusted evidence, or enforcement state is rejected, not ignored.
  • Canonical integrity failures abort the protocol call. Invalid canonical sources prevent server startup.
  • Tool results do not serialize stack traces.

MCP is not the authority surface

MCP may submit a candidate and read the state Mneme exposes. It cannot accept, reject, activate, supersede, create an exception, install a typed rule, submit trusted evidence, or bypass review. Those operations are deliberately absent from the registered tool list.

Human authority stays in the CLI. Review proposals with mneme decision proposals and mneme decision show, then use mneme decision accept or mneme decision reject. See the decision proposal workflow.

Acceptance materializes a canonical decision into project memory. It still does not install deterministic protection or run the Architecture Audit. Retrieval, authority, Audit, and enforcement remain distinct.

Downstream governance consumers

A downstream system does not need to adopt Mneme's data model, storage, or workflow to use the Decision Index. A consumer that can launch the local mneme decision-mcp process calls decision.applicable_to for a proposed change, receives the governing decisions with provenance, and folds that into whatever review, risk-scoring, or triage logic it already runs. In 0.9.0 this requires local stdio access; there is no hosted endpoint a remote service could call.

(0.9.0: the consumer must be able to launch the local stdio server; there is no remote transport a hosted service could call.)

This is the boundary the MCP server is built for: a stable protocol surface for exchanging decision context, not a shared implementation. See the integration overview for how this boundary is intended to compose with review and change-management tooling.

Known limitations in 0.9.0

Canonical-read unification: a decision accepted into .mneme/project_memory.json is available to existing runtime and Audit surfaces, but it is not automatically loaded into the MCP server's ADR-backed canonical-read index. Calling decision.get with that accepted decision ID may therefore return not_found.

Running-process freshness: a running MCP process loads its proposal state at construction. If a separate CLI process accepts or rejects a proposal, restart the MCP process before expecting MCP reads to reflect that transition.

These are bounded 0.9.0 behavior. The server does not watch files, refresh live state, or add a hidden project-memory canonical input.

For the wider protocol boundary, see Mneme's standards landscape. MCP provides interoperability; it does not define Mneme's governance semantics.
