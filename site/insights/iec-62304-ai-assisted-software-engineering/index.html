IEC 62304 and AI Coding Agents: Keeping the Record True

The FDA recognizes IEC 62304 for medical device software life cycles. Its 2023 premarket guidance says a software design specification should leave minimal ad hoc design decisions. AI coding agents make small design choices on each task, so the architecture a submission describes needs to hold on every change they write.

By Theo Valmis·December 2026

What the standard is, from the public record

The International Electrotechnical Commission (IEC) publishes IEC 62304, the international standard for the life cycle of medical device software. The full text is sold, not published, so this article relies only on what the IEC and the US Food and Drug Administration (FDA) say about it in public.

The IEC webstore entry describes a common framework of processes, activities and tasks for developing and maintaining medical device software. It applies when the software is itself a device, and when it is embedded in or integral to one. It does not cover validation and final release of the device.

The FDA keeps a recognized consensus standards database: standards it accepts for use in device submissions, each under a recognition number. IEC 62304 is recognition number 13-79. The entry covers Edition 1.1, the 2015 consolidated text that combines the 2006 first edition with its 2015 amendment. Its extent of recognition, which says whether the FDA recognizes all of a standard or only parts, is the complete standard. The same entry lists the US national adoption of the standard. With a recognized standard, a manufacturer can declare conformity to it in a submission, as the next section shows.

The recognized edition dates from 2015. AI coding agents, tools that write and edit code in a repository on a developer's behalf, became common years later. If you lead engineering at a device company and agents now write part of your device software, you need to know which parts of the life cycle record they can make untrue. This article comes from the team behind Mneme, an open-source tool that checks code changes against a team's recorded architecture decisions. The last section says what it covers and what it does not.

Where IEC 62304 appears in an FDA submission

The clearest public view of how the FDA uses the standard is its June 2023 guidance, Content of Premarket Submissions for Device Software Functions. A premarket submission is the file a manufacturer sends the FDA before marketing a device. The guidance sets two documentation levels, chosen by the risk of the device's software functions (Section V). Enhanced applies where a failure or flaw could present a hazardous situation with a probable risk of death or serious injury. Basic applies to every other submission with device software.

The guidance's Section VI (Recommended Documentation) and its Table 1 list the software documentation a submission should contain. Several elements describe how the software was built, not only what it does:

  • Software Requirements Specification (Section VI.D), with enough detail to trace requirements to the risk file, the design, the architecture chart and the tests.
  • System and Software Architecture Diagram (Section VI.E): diagrams of the modules, layers and interfaces, and how data flows between them.
  • Software Design Specification (Section VI.F), recommended in the submission at the Enhanced level, showing how the design implements and traces to the requirements.
  • Software Development, Configuration Management, and Maintenance Practices (Section VI.G).
  • Software Testing as Part of Verification and Validation (Section VI.H), Software Version History (VI.I) and Unresolved Software Anomalies (VI.J).

IEC 62304 enters at Section VI.G, and the guidance gives a sponsor two ways to cover it. The first is a summary of its own development, configuration management and maintenance practices. The second is a Declaration of Conformity: a formal statement by the manufacturer that its process conforms to the FDA-recognized version of IEC 62304, or to named clauses of it. The FDA lists those clauses by number and title. At the Basic level they include subclause 5.1.1, "Software development plan", subclause 5.1.9, "Software configuration management planning", clause 6, "Software maintenance process", and clause 8, "Software configuration management process", among others as applicable. The guidance adds that a declaration to the complete standard is not needed.

This article does not describe what those clauses require, because their text is not public. The FDA's own summary requirements for Section VI.G are public, and they are specific enough to work with.

AI in the guidance means AI in the device

The 2023 guidance does mention artificial intelligence (AI) and machine learning (ML). Every mention concerns the device's own function: what analysis method the software uses, and which data trained a model that the device runs. None concerns the tools engineers use to write the code.

The FDA's later guidance on predetermined change control plans (PCCPs) points the same way. Its final guidance applies to AI-enabled device software functions. A PCCP describes planned changes to the device, the method for developing, validating and implementing them, and an assessment of their impact. Its subject is AI-enabled software inside the product.

An agent that writes device code is a development tool. Its output enters the same life cycle record as code a person wrote, so its design choices end up in the software the FDA's architecture and design documents describe, whether or not anyone wrote those choices down. Our article on AI governance for regulated industries covers why this kind of record matters across sectors. Here the focus is the four places in the FDA's software documentation an agent touches.

Four places an AI coding agent touches the record

The tools summary. At the Basic level, the Section VI.G summary should describe the "software coding standards, methods, and tools used in software development." It should also describe the processes and tools used to link user needs, requirements, design, tests and risk controls, which the guidance calls traceability. An agent that writes production code is one of those tools. If the summary describes a process with no agent in it, the summary and the practice have drifted apart.

The design, decided in advance. Section VI.F says the design specification should make the engineers' work clear and unambiguous, "with minimal ad hoc design decisions." The guidance treats the specification as a prospective activity that guides design, development and testing, not a document written up after the code. Coding work is full of small design choices: which module to call, where to put a query, which interface to reuse. Each choice the specification did not make is the kind of ad hoc design decision the guidance asks to keep to a minimum, and an agent makes such choices on every task.

The architecture diagram. Section VI.E asks for diagrams of modules, layers and interfaces. It also covers later changes. When a manufacturer submits a modification to a cleared or approved device, one the FDA has already allowed onto the market, the diagram should identify the modules the modification affects. Suppose the diagram shows a data access layer between the user interface and the patient record store. An agent fixing a slow screen adds a direct query from the screen's handler to the store. The screen gets faster and the unit tests pass. The diagram no longer describes the software.

Change and maintenance. Regression analysis is the guidance's term for a documented evaluation of a change's impact. It draws on documents that include the source code and decides whether regression testing is needed (Section VI.H). The Section VI.G summary covers maintenance processes, including risk assessment of software changes and regression analysis. An analyst who starts from the diagram looks at the modules the design says a change can reach. The layer-crossing change above reaches a module the diagram does not connect to the screen, so an analysis based on the diagram can miss it.

The guidance does not mention AI coding agents. A team that uses them still needs the architecture decisions behind the diagram and the design specification to hold on each change, whether a person or an agent wrote it. A reviewer reading a large diff can miss one import. Architectural drift, the gradual gap between the documented architecture and the code, starts with that kind of miss.

What engineering teams can do

The list below is engineering practice, not regulatory advice. Whether a given practice satisfies a given submission is a question for a team's regulatory and quality functions.

  1. Name the agents in the development record. Describe which agents write code, on which parts of the system, and under what review. That keeps the tools summary true.
  2. Write the boundaries the diagram depends on as checkable rules. "The interface layer does not query the record store directly" is a decision a machine can check. A rule that passes or fails the same way on every run is easier to defend than a reviewer's memory.
  3. Check at two points. Check while the agent works, so it is stopped before it writes the violating file. Check again in continuous integration (CI), the pipeline that builds and tests every change, because some writes happen outside the agent. Make the CI check required, so a failing change cannot merge.
  4. Keep the verdicts with the change. A recorded verdict for each checked file, where a failure names the decision it broke, is an input to regression analysis and to the version history. It does not replace either.
  5. Keep approval with people. A check reports whether a change respects a rule. Who approved the change, and why, stays in the team's own review and quality records.

Where Mneme fits, and where it does not

Mneme enforces a team's architecture decisions on code changes, once each decision is written as a rule. It does not make software conform to IEC 62304, it does not produce a Declaration of Conformity, and it is not a quality management system.

Mneme compiles a team's architecture decision records (ADRs), short documents that each record one decision and its reasons, into one file in the repository. It enforces a decision only through an active rule: a check of a fixed kind, attached to the decision, that a machine runs the same way every time. The kind this article uses is a ban on exact text, which can be limited to certain paths and is checked both by the agent hook and in CI. A rule is active only once its ADR is accepted, not just proposed. The team switches a rule on by writing it into the ADR or by activating one Mneme proposes, and only the decision's current version is enforced.

The boundary in the example above could be written as a ban on exact text: the store's client import is forbidden under the interface layer's paths. A decision without an active rule blocks nothing.

Mneme works with Claude Code, Anthropic's coding agent, through a hook: a command Claude Code runs before the agent edits a file or runs a shell command, and again when the agent finishes its reply. Claude Code edits files with tools named Edit, Write and MultiEdit. The hook checks those calls before the write, and refuses one that breaks an active rule. It does the same for one shell form only: a single cat command that writes one file from inline text, with its end marker in quotes. Other shell writes are checked when the agent finishes its reply, after the file is written, and the agent is sent back to fix them.

The hook fails open by default: if the check itself cannot run, the edit goes through. A repository can opt in to refusing instead.

In continuous integration, mneme check, the command that tests a file against the active rules, runs on every text file a pull request adds or modifies. The documented job fails the pull request when one file breaks an active rule, and each violation names the decision. The CI setup guide keeps one machine-readable verdict per changed file as a workflow artifact, a file the CI run stores for later download. Deleted files, binary files and pushes that skip pull requests are not covered.

The Decision Index is Mneme's stored record of each decision and its versions. When a decision changes, Mneme adds a new version and leaves the earlier versions as they were. For a decision imported from an ADR, it records the source file and a hash of it. It records what each version said. It does not record who approved a decision or a change. For a device team, Mneme covers one part of the record: whether the decisions that have active rules held on each change. The development plan, risk management, testing and sign-off stay in the team's own process.

Frequently asked questions

Does the FDA recognize IEC 62304?+
Yes. The FDA's recognized consensus standards database lists IEC 62304 Edition 1.1 (2015-06, consolidated version) under recognition number 13-79, with complete recognition. The same entry lists the US national adoption.
Does FDA guidance address AI coding agents?+
The June 2023 premarket software guidance mentions AI and machine learning only as part of a device's own function. The FDA's PCCP guidance covers changes to AI-enabled device software functions. Neither addresses tools that write the code. The 2023 guidance does ask a submission's development summary to describe the tools used in software development.
Does Mneme make software IEC 62304 compliant?+
No. Mneme enforces architecture decisions that a team has written as rules, at the coding agent and in CI, and the documented CI job keeps one verdict per checked file. Conformity to IEC 62304, and the content of any submission, remain the manufacturer's responsibility and process.
