What Is the AI SDLC? Phases, Frameworks, AI-Native SDLC

The AI SDLC (AI software development lifecycle) is the familiar software development lifecycle with AI agents doing work in every phase: planning, design, implementation, testing, review and maintenance. The phases stay the same. What changes is who does the work, how fast it arrives, and where your team has to put its checks.

The six phases of the AI SDLC

The traditional lifecycle has six phases: plan, design, implement, test, review and maintain. In the AI SDLC each phase gains an AI participant. The table shows what the AI does in each phase, what people still decide, and the failure that phase is most exposed to.

PhaseWhat AI doesWhat people still ownWhat goes wrong
PlanDrafts requirements and user stories, splits work into tasksWhat is worth buildingA convincing spec for the wrong problem
DesignProposes architectures, data models and interfacesWhich architectural decisions bind the systemA design that contradicts a decision already made
ImplementWrites, refactors and migrates code across many filesWhat a change is allowed to touchCode that runs but crosses a service boundary
TestWrites tests and runs them until they passWhether the tests check the right behaviourTests written to pass, not to catch mistakes
ReviewSummarizes diffs and flags likely problemsApproving changes and granting exceptionsMore code arriving than reviewers can read
MaintainUpgrades dependencies, writes docs, helps triage incidentsLong-term direction of the codebaseEach fix drifting further from the original design

Implementation speeds up the most, because agents write code far faster than people do. The cost lands downstream. Review still runs at human speed, so review cannot keep up with AI output, and decisions that used to live in reviewers' heads stop being applied consistently unless something checks every change against them.

AI-assisted, AI-driven and AI-native

Teams use these labels loosely, and "AI-powered" or "AI-enabled" SDLC usually means the first of them. The useful difference is who starts the work and where a person checks it.

LevelWho starts the workWhere a person checksTypical tools
AI-assistedA developer; AI suggestsEvery change, in the editorAutocomplete, chat assistants
AI-drivenAn agent, given a taskAt the pull requestCoding agents such as Claude Code, Cursor and Codex
AI-nativeAgents, working from committed files such as a spec or a planAt set approval points between stages, plus automated checks on every changeSpec-driven workflows, pre-edit hooks, CI checks

In an AI-native SDLC, each stage ends by committing a file to the repository, called an artifact: an intent, a spec, a plan, or a diff with its tests. The next stage starts from it. Agents do the work between those artifacts, and a person approves at set points instead of at every step. So the rules an agent must follow have to be checked automatically on every change it makes, not only when a reviewer reads the result. Anthropic's playbook is the most detailed published version of this model; see Anthropic’s AI-Native SDLC Playbook, Summarized and Extended.

AI SDLC frameworks and methodologies

There is no single standard AI SDLC framework. Four published approaches illustrate the range. Each puts structured, written artifacts between AI steps, and most keep people approving at defined points.

FrameworkFromStructureWhere people approve
AI-DLC (AI-Driven Development Life Cycle)AWS, July 2025Three phases: Inception, Construction, Operations, worked in short cycles AWS calls "bolts"The team validates AI proposals in group sessions ("mob elaboration" and "mob construction")
AI-Native SDLC playbookAnthropic, August 2026Six stages with committed artifacts: intent.md, spec.md, plan.md, the pull request with its review findings, and a new intent.md after an incidentAt the gates between stages; hooks enforce the rules that must always hold
BMAD MethodOpen source (MIT)"Breakthrough Method for Agile AI-Driven Development": brings in product, architecture, UX, development and testing roles as the work needs themThe user directs the agents; BMAD makes key decisions explicit and carries them forward as context
Spec KitGitHub, open source (MIT)Spec-driven development: a constitution (the project’s principles), then specify, plan, tasks and implement, among other stepsThe developer reviews each step’s output before running the next

The frameworks differ in vocabulary more than in shape. All four turn intent into written requirements, a plan and then code. In each, architectural decisions mostly live in documents the agent reads, such as a constitution, an architecture document or a context file. A document the agent reads is guidance, not a check. Whether a given change respects those decisions is left to the team or to advisory review passes; none of the four checks each change against recorded architectural decisions with a rule that gives the same answer every time. That is the gap spec-driven development still leaves open.

Benefits and risks

Benefits. The gains are real when the work is well specified:

  • Faster implementation of clearly scoped changes.
  • Specs, plans and decisions written down, because agents need them as input.
  • Tests written as a matter of routine rather than when there is time.
  • Cheaper maintenance chores: dependency upgrades, migrations, documentation.

Risks. Most of them come from output growing faster than the team's ability to check it:

  • Review overload. Pull requests arrive faster than people can read them, and approval turns into a formality.
  • Architectural drift. Each change is locally reasonable, but together they move the system away from decisions the team made.
  • Weak verification. Tests that confirm what the code does rather than what it should do; see the verification tax.
  • Rework. Time saved writing code is spent fixing it later; see productivity gains and rework.

How to adopt an AI SDLC

  1. Write down the decisions agents must follow. Service boundaries, approved libraries and data-access rules belong in architecture decision records (ADRs), not in reviewers' memory. See how AI coding agents use ADRs.
  2. Choose the artifacts each stage hands on. An intent, a spec, a plan, a diff with tests. Committed artifacts give every later step, and every auditor, the same starting point.
  3. Separate advice from rules that must hold. Conventions can live in context files the agent reads. Rules that must never break need a check that runs before the change lands and gives the same answer every time, such as a hook in the agent or a check on the pull request. This is deterministic enforcement.
  4. Keep people where judgment matters. Scope, exceptions and releases need a named person; routine conformance does not.
  5. Measure outcomes, not output. Track rework, defects found after release and review time alongside throughput, so speed in one phase does not hide cost in another.

FAQ

What are the phases of the AI SDLC?
The same six as the traditional lifecycle: plan, design, implement, test, review and maintain. The AI SDLC does not add phases. Each phase gains an AI participant, and implementation speeds up the most.
What is AI in the SDLC?
AI in the SDLC means an AI system does work in any phase: drafting specs in planning, proposing architectures in design, writing code, writing tests, summarizing diffs in review, or handling migrations in maintenance. It describes where AI participates, not a new phase.
Is the AI SDLC a new methodology like Agile or DevOps?
No. Agile changed how teams organize work, and DevOps changed how code moves to production. The AI SDLC describes who, or what, does the work inside the existing lifecycle. Frameworks such as AWS AI-DLC and Spec Kit add structure on top of it, but the underlying phases stay the same.
What is the difference between the AI SDLC and the AI-native SDLC?
The AI SDLC describes agents taking part in each phase of a familiar lifecycle. In the AI-native SDLC, each phase commits an artifact the next one acts on, and agents do the work between those artifacts, with a person approving at set points rather than at every step. Checks move from human review between phases to automated checks on every change.
What is the AWS AI-DLC?
AI-DLC (AI-Driven Development Life Cycle) is a methodology AWS published in July 2025. It organizes work into three phases, Inception, Construction and Operations, run in short cycles AWS calls “bolts”, with the team validating AI proposals in group sessions.
Is the AI software development lifecycle the same as AI-assisted development?
They overlap but are not the same. In AI-assisted development a developer stays in the loop for each change while a tool suggests or completes it. In an AI software development lifecycle, agents propose specs, code, tests and reviews across the whole cycle, so the key question becomes who decides what a given change is allowed to do.
Does AI benefit every SDLC phase equally?
No. Implementation sees the biggest speed-up, because agents generate and refactor code far faster than people. Planning and design stay judgment-heavy. Review and maintenance absorb the cost: if implementation accelerates and review does not, unchecked changes pile up faster than the team can resolve them.
What goes wrong if you skip governance in the AI SDLC?
Architectural drift. Agents write code that is correct and locally reasonable but inconsistent with the wider architecture: the wrong storage layer, a forbidden dependency, a bypassed service. It stays invisible until the codebase becomes expensive to change. See Why Code Review Cannot Scale With AI Output and Review Is Not Governance.
How does Mneme fit into an existing CI/CD pipeline?
Mneme checks at two points. At edit time, a Claude Code hook that runs before each file edit checks the change against your recorded decisions and can block a violation before it reaches disk; for Cursor, the same decisions are exported as a rules file the agent reads. At pull-request time, a CI check compares the diff with the same decisions and either warns or blocks, depending on how you configure it.
