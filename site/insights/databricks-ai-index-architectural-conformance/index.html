Databricks AI Index: A Completed Task Is Not a Compliant One

The Databricks AI Index reports that among companies using its Unity Gateway, the share relying on one model provider fell from about 64% to 28% between July and November 2, 2026. Its coding benchmark compares models by cost per completed task. Neither number shows whether the completed work respected the architecture it landed in.

By Theo Valmis·November 2026

What the Databricks AI Index found

On November 16, 2026, Databricks launched the Databricks AI Index, a public record of how enterprises use AI models and what coding agents cost, which Databricks says it will update weekly. It draws on two kinds of data. The first is aggregated, anonymized usage from thousands of companies using Unity Gateway, the Databricks service through which companies reach and control the AI models they use. The second is a coding-agent benchmark built from real tasks in Databricks' own codebase.

Two figures in the launch post describe how fast model choice is spreading:

  • In July, about 64% of enterprises using Unity Gateway relied on one model provider. By November 2, that share had fallen to 28%.
  • Open-weight models, whose weights anyone can download and run, grew from 7.3% of enterprise token traffic in July to 30.9% in November.

The sample is Unity Gateway customers, and the provider count includes any provider a company has tried since July 20. And 30.9% is a share of tokens sent to Databricks-hosted models on Unity Gateway, according to the Index's chart note, not a share of companies or of all AI traffic.

Even with those limits, the figures show companies spreading work across providers. The model behind a coding task has become a choice teams revisit, and Databricks built the Index to help them make it.

What the benchmark measures

The coding half of the Index tests models across nine AI labs, run inside two agent harnesses, Claude Code and Codex. A harness is the program that runs an agent's loop and tools. Each task comes from Databricks' private codebase and is scored against hidden tests rather than by a model acting as judge. Its headline measures are task success rate and cost per completed task; it also reports average time per task.

Cost per completed task is the more useful number. Databricks shows that a low token price does not guarantee a cheap task. In its benchmark, Gemini 3.8 Flash had a low token price, yet averaged 140 turns per task and finished among the most expensive models at $11.97 per task. Extra turns, long outputs and failed attempts all add cost. Its conclusion is that no single model or harness dominates the trade-off between quality and cost, and that enterprises should test combinations against their own workloads.

That advice is more rigorous than ranking models by price per token. It leaves open one question that matters inside an existing codebase: what counts as completed.

A completed task is not a compliant one

A hidden test checks whether the code does what the task asked. It does not check whether the code does it in a way the organization has agreed to. A change can pass every functional test and still add a dependency the team banned, call a database another service owns, or replace an approved storage layer.

So a change answers three separate questions:

QuestionWhat answers itMeasured by the Index?
Which model and harness should run this task?Benchmarks, routing, budgetsYes
Does the change do what the task asked?Tests, including hidden testsYes
Does the change respect the architectural decisions already made?A check against those recorded decisionsNo

The third question is architectural conformance. The Index does not claim to measure it, and a benchmark built for all enterprises could not: every organization's decisions are different. Any team that uses the Index to choose a model inherits that limit. A model can rank well on cost per completed task because it takes the shortest path, and in a mature codebase the shortest path can be the one that crosses a boundary the team set.

Two earlier pieces cover the general argument: smart routing picks the model but not what it may build, and benchmark success is not architectural correctness. What the Databricks data adds is the economics. Once teams compare models by cost per completed task, what counts as completed sets the result.

One decision, two tasks

Mneme, the open-source tool behind this site, stores a team's architectural decisions in the repository and checks proposed changes against them. Its runnable JSON storage demo uses a project whose recorded decisions include one on storage: store data in human-editable JSON, with no external database, no object-relational mapper (ORM) and no migration layer. Two task descriptions go through the same check against it:

mneme check --memory examples/project_memory.json \
  --input examples/prompt_violation.txt --query "storage backend"
# FAIL [mneme_storage_json] · exit 2

mneme check --memory examples/project_memory.json \
  --input examples/prompt_clean.txt --query "storage backend"
# Result: PASS · exit 0

Each command reads the project's recorded decisions from project_memory.json and checks one task description against them. Exit code 2 means the check failed, here because the task breaks a recorded decision, and a hook or CI job treats that code as a block; exit code 0 means it passed. The first task asks to move storage to SQLAlchemy, PostgreSQL and Alembic. An agent could finish that refactor and pass its functional tests. It fails the check, which names the decision it breaks. The second task adds an optional expiry field inside the existing JSON store and passes. The decision record and both inputs ship in the Mneme repository, so the result can be reproduced without a model call.

The verdict depends on the decision and the input, not on which model wrote the input. That is the property a model comparison needs: a fixed yardstick that stays the same when the model changes. We have not published a comparison of models on this decision; the next two sections describe how a team could run one.

Cost per compliant completed task

Databricks divides cost by completed tasks. For a team choosing a model for its own repository, a stricter version is more honest:

Cost per compliant completed task = total cost of all attempts / tasks that pass both their functional tests and a check against the team's recorded decisions.

The total cost should include model spend for every attempt and retry, continuous integration (CI) time, the engineer time spent reviewing or correcting the output, and the run time of the conformance check itself. The denominator counts only tasks that pass both tests. This is a measurement we propose, not a result Mneme has observed, and it does not show savings on its own.

Sort every run into one of four outcomes and report the count of each next to the ratio:

Outcome per runWhat it tells you
Passed the functional tests and the decision checkCompliant completed tasks: the denominator of the measure
Passed the functional tests, failed the decision checkTasks the Index's cost per completed task would count as done, though they break a recorded decision
Failed the decision check, but a reviewer finds the change compliantFalse blocks, which are a cost of the check itself
Touched code that no recorded decision coversRuns where the measure says nothing about conformance, and which decisions to record next

The second row can reorder a model ranking. If a cheap model passes tests by crossing boundaries more often than a pricier one, its cost per completed task looks good and its cost per compliant completed task does not. Our guide on what CTOs should measure before renewing AI coding tools covers a related measure, total cost per merged change, for judging a tool budget. This one is for comparing models on the same task.

What to test before switching models

The Index recommends testing models on your own workloads. To include conformance in that test:

  • Fix the repository and the task set. Pin one commit and a set of real tasks, including some that tempt a shortcut across a known boundary.
  • Fix the decisions. Record the architectural decisions that apply, at one version, before the first run. Changing them between runs breaks the comparison.
  • Score conformance independently. Run the decision check outside the agent being tested, in CI, so a model cannot skip it.
  • Keep coverage visible. Note which agents were checked before the write and which only in CI. Report uncovered cases instead of counting them as passes.
  • Compare cost per compliant completed task next to the Index's cost per completed task. Where the two rankings disagree, the difference is the cost of drift.

Where Mneme fits

The Mneme check is deterministic: the same input against the same decisions gets the same verdict, and a failing verdict names the decision it broke. Model choice belongs to routing; model-independent governance keeps the decisions outside any one model.

Where the check runs depends on the agent, not the model. Claude Code offers a hook, a point where outside code can inspect an action first: Mneme uses it to block a file edit that breaks a decision before the edit reaches disk. OpenAI's command-line interface (CLI) coding agent, Codex CLI, gets the same check on its native patch tool. An agent can also write files by running shell commands, and most of those writes reach disk before any check; both agents check them when the agent ends its turn. For every agent, the CI check on the pull request is the backstop. The integrations page lists each agent's status and limits.

Frequently asked questions

What is the Databricks AI Index?+
A public resource Databricks launched on November 16, 2026. It combines anonymized model usage and spending data from thousands of companies using Databricks Unity Gateway with a coding-agent benchmark built from tasks in Databricks' private codebase, scored against hidden tests. Databricks says it will update it weekly.
Does the Databricks AI Index measure architectural compliance?+
No, and it does not claim to. Its benchmark measures task success against hidden tests and cost per completed task. Whether a change respects an organization's own architectural decisions depends on that organization's decisions, so each team has to measure it on its own repository.
What is cost per compliant completed task?+
A proposed measure for comparing coding models on one codebase: the total cost of all attempts, including retries, CI time and review effort, divided by the tasks that pass both their functional tests and a check against the team's recorded architectural decisions. It is a measurement framework, not an established benchmark.
