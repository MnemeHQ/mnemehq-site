From Architecture Principles to Enforceable Decisions

An architecture principle tells people what the organization intends. It gives a coding agent or a CI job nothing to pass or fail. To govern agent changes, enterprise architects have to split each principle into decisions scoped to real systems, then sort out which of those a machine can check and which stay with reviewers.

By Theo Valmis·November 2026

A principle has no pass or fail

Most enterprise architecture (EA) teams keep a list of architecture principles. One of them usually reads something like this: data access is controlled through approved interfaces. Few architects would argue with it. A principle states what the organization intends, in words broad enough to cover systems that do not exist yet.

That breadth worked while people applied the principle. A reviewer who knew the codebase could look at a pull request and say that a handler opening its own database connection broke the rule. The reviewer supplied what the principle left out: which systems it covers, what counts as an approved interface, and which shortcuts the team had already allowed.

A coding agent cannot supply any of that. Neither can a check in continuous integration (CI). Give either one the principle and it can tell you what the sentence means. It cannot tell you whether the change in front of it passes. To get a verdict, someone has to turn the principle into decisions narrow enough to fail.

What a principle leaves out

A principle, a decision and a rule answer different questions. Teams often write all three in the same document and call it a principle.

LayerExampleWhat it addsWho can check it
PrincipleData access is controlled through approved interfaces.Intent across the whole estateA person with context
DecisionIn the orders service, request handlers reach the database only through the repository layer.Scope, an owner, a reason, a lifecycleA reviewer who has read it
RuleNo file under app/handlers/ contains from app.db.client import.A construct a machine can matchAn agent hook (a check that runs inside a coding agent before it writes a file) or a CI job

The step from principle to decision adds four things. Scope says which repositories, services or paths the decision binds. An owner says who may revise it. A reason lets a later team judge whether it still holds. A lifecycle says whether it is active or has been superseded. The step from decision to rule adds one more: a construct concrete enough to match in code.

Some decisions never reach the rule layer. The architect who writes the decision should say whether it can.

One principle, several decisions

A single principle usually breaks into several decisions, one per place it bites. Take the data-access principle across three systems.

  • Orders service. Request handlers do not import the database client. They call the repository layer, which owns transactions and tenant handling.
  • Reporting jobs. Batch reports read from the reporting replica, never from the primary database.
  • New services. A service that needs direct database access records the reason and gets sign-off from the data platform owner.

Each decision names a system, a boundary and a reason. Each one is also checkable to a different degree, which the next section sorts out.

The orders decision is the easiest. Mneme, an open-source tool that checks code changes against a team's recorded architecture decisions, documents this exact case. Its how-to guide writes the decision as an architecture decision record (ADR), a short document that states one decision and its reason; see Turn an ADR into an enforceable decision. The ADR keeps its prose and adds one typed rule: a rule in a fixed format that a program can evaluate. This one is a FORBID_LITERAL rule, which names exact text that must not appear and the paths where the ban applies:

## Constraints
- FORBID_LITERAL:
    value: from app.db.client import
    include_paths:
      - "app/handlers/**"

When a handler adds that import, mneme check, Mneme's command that tests a file against the recorded decisions, fails and names the decision. The guide's recorded output begins:

FAIL  [ADR-012] FORBID_LITERAL "from app.db.client import" -- trigger: from app.db.client import
      Request handlers do not import the database client
      path: app/handlers/invoices.py via app/handlers/**

The same file saved under app/repositories/ passes, because the rule's paths do not cover it. The principle never said where the boundary sat. The decision does, and the rule makes it testable.

Sort decisions by what a machine can decide

Mneme also ships the Architecture Protection Audit (the Audit, below), which scans a repository's recorded decisions and puts each one into one of four states. The states work as a sorting key for decisions derived from a principle, whether or not you use Mneme.

StateMeaningData-access example
ProtectedA typed rule exists on the decision, and the Audit verified itThe orders handler rule above: the guide's audit reports ADR-012 as Protected once the ADR is imported
Mneme-readyOne concrete rule can express it without guessing; the Audit proposes that rule, but nobody has activated itThe orders decision written as prose only, if the Audit can derive the rule from its wording
Requires modellingThe intent is mechanical, but it needs narrower scope before a rule can express it safelyThe reporting-replica decision: a check needs to know which connection names point at the primary
GuidanceIt depends on judgment and should stay with peopleThe new-service decision: whether a reason is good enough is a human call

Guidance is an end state. A decision about sign-off for a new service will never reduce to a text match, and forcing one would produce a rule that blocks good changes and passes bad ones. Keep it in review, with a named owner. Four architecture protection states explains what moves a decision from one state to another.

Once every decision under a principle has a state, the principle gets a profile. Data access might come out as one decision Protected, one Requires modelling and one Guidance. That profile tells you how much of the principle a machine enforces today, and where the rest depends on a reviewer remembering it.

Keep the link back to the principle

If you cut a decision off from its principle, the next team inherits a rule with no stated purpose. If you cut a principle off from its decisions, nobody can say where it applies. Keep references in both directions.

  • Each decision cites its principle. Put the principle's name in the ADR's frontmatter or first paragraph. When someone asks why handlers cannot import the client, the answer leads to an intent the organization agreed.
  • Each principle lists its decisions. The EA repository or wiki entry for the principle links to every ADR that implements it, with the state of each.
  • Each verdict names its decision. A failed check that says which decision it enforced, and which version, lets a reviewer follow the chain from a line of code to the principle above it.

The reverse link matters most when a principle changes. If data access moves to a new platform, the list tells you which decisions to revise and which rules to retire. Without it, old rules keep firing against a principle the organization has already replaced.

This map lives in your own repositories and wiki. ISO/IEC/IEEE 42010:2022, the international standard for architecture descriptions, says it does not specify the methods or tools used to create them. The Open Group's TOGAF Standard is an EA methodology and framework, and its ArchiMate Specification is a modelling language. None of the three is a tool that checks a repository. Turning a principle into a check is your team's work.

What architecture teams should do now

  • Pick one principle that agents break. Data access, service ownership and approved dependencies are common starting points.
  • Write one decision per system it binds. Give each a scope, an owner, a reason and a status. Cite the principle in each.
  • Sort each decision into a state. Install rules for the ones a machine can check, scope the ones that need modelling, and name a reviewer for the guidance.
  • Report per principle. Show how many of its decisions run as checks and how many depend on review. Review that profile when the principle changes.

Where Mneme fits

Mneme, an open-source decision and control layer for agentic software development, works at the decision and rule layers inside a repository. It does not hold your principles, model your business capabilities or replace your EA tools.

Mneme imports ADRs into the Decision Index, its persisted, versioned record of a repository's decisions. The index keeps each decision's lifecycle status and, for a decision imported from an ADR, the source file and its content hash (a fingerprint that changes if the file's text changes). A decision that carries an active typed rule is enforced in CI, and before the write lands when a supported coding agent edits through its own file tools; the integrations page lists which agents and which paths. Each verdict names the decision and rule it enforced. The Audit classifies every decision it finds as Protected, Mneme-ready, Requires modelling or Guidance.

Two limits matter for EA teams. The Decision Index records what each decision version said and where it came from, but not who approved it, so keep approvals where identities are verified, such as pull request review on the ADR files. And the link from a decision up to an enterprise principle is a convention you keep in the ADR text today, not a field Mneme tracks.

Frequently asked questions

Can an AI coding agent follow architecture principles?+
An agent can read a principle and try to follow it, but nobody can check whether it did. A principle has no scope and no construct to match. To check a change, turn the principle into decisions scoped to specific systems, and give the checkable ones a rule a machine can evaluate.
What is the difference between an architecture principle and an architecture decision?+
A principle states intent across the whole organization, such as controlled data access. A decision applies that intent to one system, with a scope, an owner, a reason and a lifecycle. One principle usually produces several decisions.
Which architecture decisions should stay with human reviewers?+
Decisions that depend on judgment, such as whether a reason for an exception is good enough. Mneme's Audit calls these Guidance. Keep them in review with a named owner, and spend machine checks on decisions that reduce to a concrete construct.
Where do ISO/IEC/IEEE 42010 and TOGAF fit in enforcing architecture in code?+
ISO/IEC/IEEE 42010:2022 sets requirements for architecture descriptions and states that it does not specify the methods or tools used to create or use them. The Open Group describes TOGAF as an enterprise architecture methodology and framework. Neither is a tool that checks a repository against a decision; that check is separate work.
