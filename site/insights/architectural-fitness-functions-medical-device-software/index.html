Architectural Fitness Functions for Medical Device Software

FDA guidance recommends that device makers document their software architecture: its modules, layers and data flows. AI coding agents change that structure one shortcut at a time. Architectural fitness functions, automated checks on a property of the design, can keep the code matching what the team documented.

By Theo Valmis·December 2026

An architectural fitness function is an automated check that keeps one property of a system's design true as the code changes, such as which module may import which. This article shows how a medical device team can write such checks from the architecture it has already documented for the US Food and Drug Administration (FDA), and why that matters once AI coding agents are editing the code.

The architecture you already wrote down

Before many medical devices can be sold in the US, the maker files a premarket submission: the application the FDA reviews, for example before deciding whether the device may go on the market. When the device includes software that itself meets the legal definition of a device, the FDA calls that software a device software function. The FDA guidance Content of Premarket Submissions for Device Software Functions, finalised in June 2023, recommends a system and software architecture diagram in every such submission. Its section on the diagram says the diagram should make clear four things:

  • the modules and layers that make up the system and software;
  • the relationships among those modules and layers;
  • the data inputs, outputs and flows among them;
  • how users and external products, such as IT infrastructure and connected devices, interact with the system.

That is a statement of intended structure. Two other passages expect the documented design to come first and the code to trace back to it. The first concerns the Software Design Specification (SDS), the document that says how each requirement is implemented. It should leave "minimal ad hoc design decisions", and the guidance expects it to be written before the design is built, not "documented retrospectively".

The second is the guidance's definition of software verification: confirming, with objective evidence, that each development phase produced what its inputs required. Verification activities, it says, include technical evaluations of the software architecture. They also include traceability analyses, which check that each piece of source code maps to a part of the SDS and back.

How much of this goes into the submission depends on risk. The guidance sets two documentation levels. Enhanced Documentation applies where a failure or flaw in a device software function could present a hazardous situation with a probable risk of death or serious injury. At that level the full SDS goes into the submission, along with every unit and integration test protocol and report. Basic Documentation applies everywhere else: the SDS stays in the team's own design records, and the submission carries a summary of testing and the system-level test protocol instead of every unit and integration protocol.

None of this tells a team how to write its code. The scope section says the guidance does not recommend any specific software life cycle model or development methodology. The method is the team's choice. One practice a team may choose is to turn its documented architecture into automated checks that run on every change. That practice is not an FDA requirement, and nothing here is regulatory advice.

Where AI coding agents strain the picture

An AI coding agent works from the task in front of it. Asked to show a new reading on the device's display, it looks for the shortest path to the data. If the result-interpretation module has an internal function that returns the value, the agent may import it straight into the user interface module. The feature works and the tests pass. The architecture diagram in the design history file (DHF), the record of how the device was designed, now describes a dependency direction the code no longer follows.

This is the ad hoc design decision the SDS passage warns about, made in seconds and without a record. One such change is easy to catch in review. An agent can open dozens of changes a week, though, and a reviewer reading a correct diff has no reason to compare it against a diagram drawn two years earlier. Our overview of AI governance for regulated industries argues that once code drifts from the design a team verified, the problem is accountability. This article covers one mechanism for keeping the implemented structure and the documented one the same.

Fitness functions, in brief

The term comes from evolutionary computing. Neal Ford, Rebecca Parsons and Patrick Kua applied it to software architecture in Building Evolutionary Architectures (O'Reilly, 2017; a second edition added Pramod Sadalage). The book describes an architectural fitness function as one that provides an objective integrity assessment of one or more architectural characteristics. That can be a test, a metric or a monitor that checks a property of the architecture. Our Architecture as Code concept page covers the idea and its tooling in more depth.

The common structural kind is a dependency check. ArchUnit, a Java library that runs inside an ordinary unit test framework, can check dependencies between packages and classes, between layers, and between slices (groups of classes selected by package name, such as one per feature). It can also find cyclic dependencies. In other languages, an import linter does a similar job: a tool that reads each file's import statements and fails when one crosses a boundary the team has declared. These tools fit a device team well because the rule they check is the same rule the architecture diagram already states.

Four fitness functions to derive from your documents

Each one below starts from a document the team already maintains for its submission: the architecture diagram, the SDS, the list of third-party software and the change records. The device is fictional: a handheld diagnostic reader with four modules, signal processing, result interpretation, user interface and cloud upload.

  1. Dependency direction between layers. The diagram shows the user interface calling result interpretation through a published interface. A fitness function fails the build when any user interface file imports from the module's internal package. This is the check that catches the agent's shortcut above.
  2. Declared data flows. The diagram shows one module, cloud upload, talking to the network. A fitness function fails when any other module imports the HTTP client or socket library. A developer who needs a new network path has to change the check, and that change is the prompt to update the diagram in the same review.
  3. Off-the-shelf software. The guidance defines off-the-shelf (OTS) software as a generally available component, such as an operating system or a display library, for which the manufacturer cannot claim complete life cycle control. A fitness function compares the dependency manifest against the list of OTS components the team has assessed and fails on anything new. An agent will add a package to finish a task; this check makes a person decide whether the package stays.
  4. Modified modules against the change record. A device the FDA has already allowed onto the market, through clearance or approval, is a cleared or approved device. For a submission about a change to one, the guidance says the diagram should identify the modules the change affects. A fitness function can compare the modules a code change touches with the modules its change record names, and flag the difference for review.

Run them in continuous integration (CI), the pipeline that builds and tests every change, and keep the results with the software version they ran against. The guidance asks for a software version history that lists the versions tested and what changed between them. A result per check, per version, is evidence a team can file next to that history. Whether it satisfies a given submission is for the team's regulatory function to judge.

What fitness functions do not do

Fitness functions detect. A CI check runs after the code exists, often after the agent has moved on to the next task, and the failure lands on whoever reads the pipeline. A check can find a violation without having the authority to prevent it.

Most are also anonymous. A test named test_ui_does_not_import_interpretation_internals encodes a decision, but nothing ties it to the record of who made that decision, why, and which document it came from. When the diagram changes, the test may not. When someone deletes the test to get a build green, nothing in the record notices. For a team that must trace code back to its design, the link from each check to its decision matters as much as the check.

And a passing suite proves only what it checks. Four fitness functions do not establish that the software is safe, that the submission is complete or that a standard has been met. The life sciences article covers why evidence must be proportional to risk; fitness functions are one input to that judgment, not a substitute for it.

IEC 62304 is the International Electrotechnical Commission (IEC) standard for medical device software life cycle processes. The FDA guidance lets a sponsor state formally that it follows parts of it, in a declaration of conformity. The standard sets its own process obligations, which this article does not cover.

Where Mneme fits

Mneme is an open-source tool that checks code changes, including an AI agent's edits, against the architecture decisions a team has written as machine-checkable rules. It addresses two of the gaps above: it links each check to a decision, and it can run the check before an agent's edit lands.

It ties each check to a decision. The team writes the decision as an architecture decision record (ADR), a short Markdown document that records one decision and its reasons. The ADR gets a section headed "Constraints", and each entry there states one machine-checkable rule. One kind of rule is FORBID_LITERAL: exact, case-sensitive text that must not appear in the files the rule covers, which optional path selectors can limit to named directories.

For the reader above, that could be the import line for the interpretation module's internal package, limited to the user interface directory. Once the ADR is marked accepted and the team imports it, the rule is active, and Mneme checks changes against it. Each violation it reports names the decision, the rule and the text that triggered it.

It checks agent edits before they land, and again in CI. A pre-write hook is a script the coding agent runs before it writes a file, which can refuse the write. Mneme ships these hooks for Claude Code, the Claude Agent SDK, Codex CLI (OpenAI's command-line coding agent), the Kiro CLI 3.0 engine and Google Antigravity.

In Claude Code, the hook refuses a file edit that breaks an active rule before the file changes: an Edit, Write or MultiEdit call, or one shell form, a single cat heredoc write with a quoted delimiter. Other shell writes are checked when the agent ends its turn, after the file already exists, and the agent is sent back to fix them. The hook fails open by default: if the check cannot run, the edit goes through. The CI job runs the same check on every text file a pull request adds or modifies.

The coverage has limits. The CI job does not check deleted files, binary files or pushes that skip pull requests. Rules match exact text: a rule for from interpretation.internal import does not catch import interpretation.internal as ip, so a team adds one rule per import form or keeps an import linter alongside. Checks for layering in general, cycles, coupling or dependency manifests stay with ArchUnit, import linters and the team's own tests. Mneme does not produce submission documents, does not assess OTS software and does not establish conformity with any standard or regulation.

What to do this quarter

  1. List the rules your diagram already states. Go through the architecture diagram and the SDS and write down every dependency direction, data flow boundary and module boundary they assert.
  2. Write a fitness function for each one a tool can check. Start with dependency direction and network access: the diagram states both directly, and both are simple to check.
  3. Name the decision behind each check. Give every fitness function a reference to the decision record and the document section it protects, so a change to one prompts a review of the other.
  4. Put the checks in front of the agent as well as behind it. A CI failure after the fact costs a rework cycle. A check when the agent writes the file sends it back before the change exists.
  5. Protect the checks themselves. Name owners for the fitness function files, the CI workflow and the decision records (on GitHub, in a CODEOWNERS file), and require their approval on any change to them, so an agent cannot make a build pass by editing the test.

Frequently asked questions

What is an architectural fitness function?+
A test, metric or monitor that gives an objective assessment of an architectural characteristic, such as dependency direction between layers. The term comes from evolutionary computing; Neal Ford, Rebecca Parsons and Patrick Kua applied it to software architecture in Building Evolutionary Architectures.
Does the FDA require fitness functions?+
No. The FDA's 2023 guidance on premarket submissions for device software functions says what to document, including a system and software architecture diagram, and states that it does not recommend a particular development method. Fitness functions are an engineering practice a team may choose to keep its code consistent with that documentation.
Which fitness functions should a medical device team write first?+
Start with the rules the architecture diagram already states: dependency direction between layers and which modules may reach the network. Then add a check that new off-the-shelf components match the list the team has assessed.
Does Mneme make medical device software compliant?+
No. Mneme enforces accepted architecture decisions written as exact-text rules, before supported agent edits and in CI, and names the decision in each violation it reports. It does not produce submission documents or establish conformity with any standard or regulation.
