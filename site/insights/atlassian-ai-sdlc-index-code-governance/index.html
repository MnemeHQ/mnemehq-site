Atlassian AI SDLC Index: Review Is Measured, Architecture Is Not

The Atlassian AI SDLC Index, built on data from more than 340,000 engineers, shows each reviewer handling 22.3 pull requests a month in October, up from 12.8 in January. Its review figures count speed and volume. None shows whether a merged change kept to the architecture, and that is the number engineering leaders need to add.

By Theo Valmis·November 2026

What the Atlassian AI SDLC Index measures

On November 16, 2026, Atlassian published The Atlassian AI SDLC Index, a dashboard of how the AI software development lifecycle (SDLC) is changing, and updated it on November 18. The data comes from DX, a platform engineering organizations use to measure developer productivity and AI use. Atlassian describes the sample as more than 340,000 engineers at more than 500 engineering organizations that use DX.

Some figures are self-reported by developers. Others come from product data, such as when a pull request (PR) first gets a human review.

That makes the Index a different kind of evidence from Atlassian's earlier report, The Agentic Pivot. The Agentic Pivot was a survey of more than 1,100 software professionals, engineering leaders and individual contributors, about how they use and govern AI. The Index adds measured product data, and some of its charts run month by month. Four of its figures bear on code review.

Review load per reviewer rose by about three quarters between January and October. Time to first review climbs at every step of AI share in the chart: 31.2 minutes, then 66.6, then 72.6, then 97.8. In the friction breakdown, developers rank review wait time joint first with continuous integration (CI) wait time, at 86.5 hours a year each. Code comprehension comes next, at 71.5 hours.

Two cautions apply. The review-time chart is observational. Companies that write most of their code with AI may differ from the rest in size, process or staffing, so the Index does not show that AI authorship causes slower reviews. And each chart has its own sample, from 180 to 630 companies, with every figure aggregated at company level, so the 69.7% and the 22.3 describe different sets of companies.

Automated review is growing too. Among companies that use bot reviewers on more than 5% of PRs, the share of PRs with a bot review rose from 15.3% in November 2025 to 21.2% in October 2026. AI is also being used for design work itself: architecture design and planning appears in 11.9% of AI sessions in the Index's breakdown of tasks.

What the Index does not measure

Every review figure in the Index counts speed or volume: how many PRs, how long until someone looks, how many hours lost to waiting. None of them asks whether a merged change kept to the decisions the system was built on.

The nearest figure is code survivorship. In October, 68.2% of AI-authored code survived. Atlassian defines survivorship as the share of AI-authored code that remains in commits. That tells you the code was kept. It does not tell you the code was correct, safe or consistent with the architecture. Code that crosses a boundary the team agreed on can survive for years.

DX can count review events because each PR leaves a record in the tools a team already uses. An architectural violation leaves no record unless someone wrote the decision down in a form a tool can check. Where a team has not done that, there is nothing for any platform to count.

The Index can time your reviews. It has no way to see whether those reviews kept your architecture intact.

Why faster review is not enough

A reviewer, human or bot, checks a change for several different things: whether it compiles and passes tests, whether it introduces a security flaw, whether it is maintainable, and whether it fits the system's architecture. Automated review can judge the first three from the code in front of it.

The fourth needs knowledge the diff does not contain. Suppose a team decided, after an incident, that domain code must never import infrastructure adapters. It calls an interface the domain owns, and the adapter sits behind it. An agent adds a feature, imports the database adapter into a domain module because it is the shortest path, and writes passing tests. The change is correct in every way a bot can see. It breaks a decision the bot was never shown.

We have argued elsewhere that code review cannot scale with AI output, and that output now moves faster than teams can explain it (see When AI Builds Faster Than Engineers Can Understand). The Index adds measured data to that argument. It also shows where the measurement stops: a team can watch its review times by the month and still have no number for architectural conformance.

Five metrics to track next to the Index

An engineering leader can use the Index as a benchmark for the first two metrics below. The other three are our proposal. DX does not measure them, and they are not validated benchmarks, but each can be counted from records a team can keep.

MetricWhat it showsSource
PR review loadDistinct PRs each reviewer handles per monthMeasured in the Index
Time to first human reviewHow long changes wait for a personMeasured in the Index
Decision protection coverageShare of recorded architectural decisions that have a machine check behind themProposed
Violations caught before mergeHow many changes broke a recorded decision and were stopped before they mergedProposed
Changes needing architectural judgmentShare of changes that touch a decision no check can settle, so a person who owns it must review themProposed

Read together, the five show whether rising review load is a staffing problem or a design problem. If load climbs while protection coverage stays flat, reviewers are carrying the architecture in their heads, one PR at a time. If coverage rises, the checkable decisions leave the review queue and people spend their time on the changes that need judgment. From a decision to a check

Take the domain-layer decision above and follow it through. The steps below use Mneme, the open-source tool we build, which stores a team's architectural decisions in its repository and checks code changes against them. Other tools can play the same role.

  1. Record it. The team writes the decision as an architecture decision record (ADR): domain code does not import infrastructure adapters, with the incident that prompted it as the reason.
  2. Make the checkable part exact. The decision gets a typed rule, a version of it a machine can check. Here the rule forbids the exact text from app.infrastructure in files under app/domain/.
  3. Check every change. When an agent's change adds that import to a domain file, the check returns a FAIL. Some coding agents let an outside check inspect each file write before it happens, known as a pre-write hook. There, the write is stopped before it lands. In CI, the PR fails.
  4. Show the reviewer the decision. The verdict names the decision that produced it. The reviewer does not have to know the rule exists, or spot the import on a busy afternoon.

The limits matter as much as the steps. A literal rule catches that exact text. An import written another way, through an alias or a relative path, would not match, and a decision that is a judgment call has no rule at all. Those stay with the people who own the decision. The aim is narrower: take the decisions a machine can settle out of the review queue, so the 22.3 PRs a month get human attention where it counts.

What engineering leaders should do

  • Read the Index for direction, not for your own baseline. Its figures are company-level aggregates from different samples. Measure review load and time to first review in your own systems before comparing.
  • Add one architecture metric to the review dashboard. Start with decision protection coverage. It comes from records a team already keeps, and it shows whether review is carrying load a check could carry.
  • Record the decisions agents break most. Data access, layer boundaries and approved dependencies are good first candidates. Write each with its scope and its reason.
  • Route the rest to owners. Changes that touch a decision no check can settle go to the person who owns that decision, not to whoever is free.

Where Mneme fits

Mneme describes itself as a decision and control layer for agentic software development. In this article's terms, it works on the checkable part of the problem: it does not replace code review, and it does not make judgment calls.

A decision is enforced when it carries an active typed rule: exact, case-sensitive text that must not appear in code, optionally limited to certain paths. A matching change returns a FAIL that names the decision behind it. A decision without an active typed rule is not enforced. The checks run in CI on pull requests, and before a write in coding agents with a supported hook, such as Claude Code and Codex CLI. The integrations page lists which writes each agent's hook covers.

The Architecture Protection Audit reports the closest measure for a repository. It reads the decisions already recorded there, sorts each one as Protected, Mneme-ready, Requires modelling or Guidance, and reports the share of the non-Guidance decisions that are already Protected. Protected means a typed rule already enforces the decision. Mneme-ready means a rule could be written from it as recorded. Requires modelling means it is a firm rule that needs a precise form first. Guidance is advice, not a rule. The free ADR checker sorts the statements in one pasted ADR into the last three groups.

Frequently asked questions

What is the Atlassian AI SDLC Index?+
A dashboard Atlassian published on November 16, 2026, and updated on November 18, built on DX data from a sample of more than 340,000 engineers at more than 500 organizations that use DX. It tracks AI use, developer friction, PR review load and time, AI code survivorship and AI spend. Some figures are self-reported and some come from product data, all aggregated at the company level, and each chart has its own sample.
Does AI-written code make code reviews slower?+
The Index shows an association, not a cause. Median time to the first human review is 31.2 minutes at companies where 20 to 40% of code is AI-written and 97.8 minutes where it is 80% or more. Those companies may differ in other ways, such as size or staffing, so the data does not show that AI authorship causes the delay.
Why does AI-generated code still need human review?+
Automated review judges what it can see in the code: whether it passes tests, whether it has a known security flaw, whether it is maintainable. Whether a change keeps to an architectural decision depends on knowledge the diff does not contain. Decisions that can be written as exact checks can be enforced by a machine; decisions that need judgment still need the person who owns them.
What is AI code governance?+
Making sure AI-generated changes keep to the decisions an engineering organization has already made: recording those decisions, turning the checkable ones into rules, checking every change against them before merge, and routing the rest to the people who own them. Code review checks a change; governance decides what every change must preserve.
