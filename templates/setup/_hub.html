The three places Mneme runs

An active rule is a check you have switched on for a decision, such as “the word celery must not appear in code”. Mneme checks a change by comparing it with your active rules, and blocks it by refusing the edit or failing the pull request. The hook and the CI check can block; the lookup server never does. Start with any one, and the guides add the others.

  • Agent hookCore

    Blocks a bad edit while the agent works

    A hook is a command your coding agent runs before it edits a file. Mneme’s hook refuses an edit that breaks an active rule. What it catches differs by agent, and some agents have no Mneme hook.

  • CI checkCore

    Fails a bad pull request before merge

    A job in your pipeline runs mneme check on each file a pull request adds or modifies. It catches what the hook missed, and changes from agents and people with no hook.

  • MCP lookup serverOptional

    Shows agents the decisions; blocks nothing

    A local server, mneme decision-mcp, that speaks the Model Context Protocol (MCP). An agent can search decisions, ask which ones apply to a file, and propose new ones for people to review.

What you install

Your decisions are architecture decision records (ADRs): short Markdown files in docs/adr/. Mneme compiles them into one memory file, .mneme/project_memory.json, which the hook, the CI check and the lookup server all read.

A decision blocks nothing until it has an active rule. The guides take one decision through four commands: mneme setup creates the memory file, mneme adr import adds your ADRs, mneme protect validate tests the rule Mneme proposes without changing anything, and mneme protect activate switches it on. You can also write the rule yourself in the ADR, under a ## Constraints heading, for example FORBID_LITERAL: celery, which bans that exact word; a rule written this way is active as soon as you import it.

What no setup guarantees

Before you rely on any of it, test one blocked and one allowed change in your own repository. Every guide shows both. Three limits apply everywhere:

  • Hooks fail open by default: if the check itself can’t run, the hook lets the change through instead of blocking it. If a check crashes or times out, the Claude Code hook allows the edit, and the Codex CLI hook lets it through with an unevaluated note. Claude Code has an opt-in mode that refuses direct file writes when the check can’t run; turning it on takes a reviewed change on your default branch.
  • Some writes are not stopped before they land. Most shell commands and scripts reach disk first. Claude Code and Codex CLI check them when the agent ends its turn; with other agents, only CI sees them.
  • CI covers only what your pipeline runs on: the files a change adds or modifies, in the repositories and branches where the job is required.
