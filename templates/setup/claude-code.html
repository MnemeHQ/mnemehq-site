Goal

This is the reference setup: the one we recommend first, because Claude Code is the agent with Mneme’s most complete hook. The example decision bans Celery, a task-queue library, from the codebase. By the end, the same rule stops Claude Code from writing it and fails any pull request that adds it.

Two layers are required here. The hook is a command Claude Code runs before it edits a file; Mneme’s blocks an edit that breaks an active rule. The CI check runs in your pipeline and catches what the hook can’t see. A third layer, the decision lookup server, is optional, and step 7 covers it.

Prerequisites

  • Python 3.11 or newer, and pipx.
  • Claude Code, the command-line agent. The Claude web, desktop and mobile apps don’t run plugin hooks.
  • A git repository on GitHub or GitLab, with permission to add a CI workflow and make it a required check.

Tested versions: the Mneme commands and hook replays below ran against mneme-hq 0.11.0 on Windows, with the recorded output shown. Installing the plugin from Claude’s plugin directory and running Claude Code itself were not part of that run; the plugin calls the same mneme-hook command shown here.

Configure

1. Install the command-line tool

pipx install "mneme-hq==0.11.0"

This installs mneme and mneme-hook, the command the plugin runs. pipx puts both on your PATH, where Claude Code can find them.

2. Write one ADR

Save this as docs/adr/ADR-001-no-celery.md. Its title, No Celery, names one banned term, which is what lets Mneme propose a rule for it.



    
3. Set up, import, audit, validate and activate

    
Install Mneme and activate your first protection explains each of these commands and its output. In short, from the repository root:

    
mneme setup
mneme adr import docs/adr --memory .mneme/project_memory.json --apply
mneme audit --memory .mneme/project_memory.json --repo-root .
mneme protect validate ADR-001 --memory .mneme/project_memory.json
mneme protect activate ADR-001 --memory .mneme/project_memory.json

    
mneme setup creates the memory file, .mneme/project_memory.json, and blocks nothing. The audit reports ADR-001 as Mneme-ready, meaning it found a rule it could install. Validation tests that rule and changes nothing. Activation installs it:

    

    
Commit the ADR and .mneme/project_memory.json. The installed rule lives in the memory file, and the hook and the CI check both read it.


    
4. Install the Claude Code plugin

    
claude plugin install mneme@anthropic-plugin-directory

    
The plugin adds the hook and four slash commands, including /mneme:context, which looks up the decisions for a task. It starts in strict mode, which blocks. The plugin does not install the command-line tool, so step 1 is still needed: without it the plugin installs cleanly and checks nothing.

    
To pin the plugin to the 0.11.0 release instead, load it from a checkout:

    
git clone --branch v0.11.0 --depth 1 https://github.com/MnemeHQ/mneme mneme-src
claude --plugin-dir ./mneme-src/integrations/claude-code-plugin


    
5. Start Claude Code from the repository root

    
The hook looks for .mneme/project_memory.json in the session’s working directory and its parents. Start Claude Code inside the git repository, too: the end-of-turn check compares against git.


    
6. Add the required CI check

    
Copy the workflow for GitHub Actions or the job for GitLab CI from the CI-only setup, then make it required: a branch ruleset with “Require status checks to pass” on GitHub, or “Pipelines must succeed” on GitLab. Without that setting, a failing check is only a red mark on the pull request.


    
7. Optional: add the decision lookup server

    
/mneme:context already gives Claude Code the decisions for a task. The Model Context Protocol (MCP) server adds lookup by file path, tracing which decision replaced which, and proposals for people to review. The decision MCP setup shows the .mcp.json entry Claude Code reads.

  


  

    
Run

    
Ask Claude Code for a change that breaks ADR-001, for example: “Add a worker in workers/jobs.py that uses Celery.” When the agent goes to write the file, Claude Code sends the hook a JSON description of the call. To see the hook’s answer without running an agent, save that event as events/write-celery.json:

    

    
mneme-hook < events/write-celery.json

    
Then the allowed version, the same worker on Pub/Sub, saved as events/write-pubsub.json:

    

    
mneme-hook < events/write-pubsub.json

    
Finally, open a pull request that adds both workers as workers/jobs.py and workers/publish.py, so the CI check has one file of each kind.

  


  

    
Expected result

    
The Celery write exits with code 2, which Claude Code treats as “block this change”. The file isn’t written, and the agent receives this text:

    

    
The Pub/Sub write exits 0 with no output, so the agent carries on.

    
In CI, the check prints one line per changed file with the exit code mneme check returned, and the job fails with exit code 2:

    

    
We ran the workflow’s check loop against a local copy of that pull request, not on GitHub’s runners.

  


  

    
What is and isn’t enforced

    
    
      
  • Blocked before the file changes: Edit, Write and MultiEdit calls, and one shell form, a single cat > file <<'EOF' command with a quoted delimiter.
    • 
      
  • Checked only when the agent ends its turn: other shell writes, such as echo >, sed -i or a script. The file already exists by then; the hook sends the agent back to fix it and doesn’t undo the write. Stop an AI coding agent from crossing an architectural boundary replays this end-of-turn check.
    • 
      
  • Fails open: if mneme isn’t found, a check crashes, or a check takes longer than 10 seconds, the hook allows the edit. Its notes go only to Claude Code’s debug log.
    • 
      
  • Not covered by the hook: changes made outside Claude Code, by people or other tools. The CI check covers those, for the files a pull request adds or modifies.
    • 
      
  • The rule matches exact text. celery as a whole, case-sensitive token, in any file except the ADR and the memory file. It doesn’t match Celery on its own, and a comment that mentions celery fails too.
    • 
    

  


  

    
Troubleshooting

    
Nothing is blocked, and the hook prints nothing

    
The hook didn’t find a memory file, and with none it allows every change silently:

    
MNEME_MEMORY=missing.json mneme-hook < events/write-celery.json

    

    
The output is empty and the exit code is 0. Start Claude Code from the repository root, or set MNEME_MEMORY to the memory file’s path.

    
The edit goes through, and nothing explains why

    
Warn mode is on, through MNEME_HOOK_MODE=warn or the plugin’s mode option. The hook then defers to Claude Code’s normal permission flow, and Claude Code doesn’t show the reason it attaches:

    

    
Unset the variable or set the option back to strict.

    
The hook isn’t firing at all

    
Check that mneme-hook is on your PATH (which mneme-hook, or where mneme-hook on Windows) and that claude plugin list shows mneme@anthropic-plugin-directory. If the audit still says Mneme-ready rather than Protected, the rule isn’t active yet: repeat step 3.

    
CI fails on every pull request at the memory check

    
An ADR changed without a re-import, or ADR line endings differ between machines. The CI-only setup covers both.
