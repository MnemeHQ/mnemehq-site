Goal

Codex CLI writes files mainly through apply_patch, its built-in tool for adding and changing files. Mneme’s Codex hook checks those patches before they run. At the end of each turn, when Codex finishes responding and fires its Stop event, the hook checks every file the session changed, which catches shell and script writes. The example decision is ADR-001, an architecture decision record (ADR) that bans the Celery library.

Mneme 0.11.0 ships the Codex hook as a Python module, with no installer and no published configuration. You register it yourself, as this guide shows.

Prerequisites

  • Python 3.11 or newer, and Codex CLI.
  • A git repository. The next section adds a decision with an activated rule.
  • Permission to add a CI workflow and make it a required check.

Tested versions: Mneme’s own validation ran the hook against Codex CLI 0.149.1 on Windows through codex exec, 10 runs out of 10. Interactive sessions, other platforms and other Codex versions are not separately proven. For this guide we ran the hook commands below against mneme-hq 0.11.0 by piping Codex events to it; we did not run Codex itself.

Configure

1. Install Mneme where the hook can find it

The hook runs as a Python file, so Codex needs the path of a Python interpreter that has mneme-hq installed. A dedicated virtual environment makes that path stable:

python -m venv ~/.mneme-venv
~/.mneme-venv/bin/python -m pip install "mneme-hq==0.11.0"

On Windows the interpreter is .mneme-venv\Scripts\python.exe. This environment also gives you the mneme command for the setup steps. Then print the two paths the hook configuration needs:

~/.mneme-venv/bin/python -c "import sys, mneme.integrations.codex_cli.hook as h; print(sys.executable); print(h.__file__)"

The first line is the interpreter, the second the hook file. On our Windows test machine they ended in venv\Scripts\python.exe and site-packages\mneme\integrations\codex_cli\hook.py. Step 3 writes both into the configuration for you.

2. Add one decision with an activated rule

Save this architecture decision record as docs/adr/ADR-001-no-celery.md:


    
Then, from the repository root, create the memory file (.mneme/project_memory.json, where Mneme compiles your decisions), import the ADR, and validate and activate its rule. This decision blocks nothing until its rule is activated:

    
~/.mneme-venv/bin/mneme setup
~/.mneme-venv/bin/mneme adr import docs/adr --memory .mneme/project_memory.json --apply
~/.mneme-venv/bin/mneme protect validate ADR-001 --memory .mneme/project_memory.json
~/.mneme-venv/bin/mneme protect activate ADR-001 --memory .mneme/project_memory.json

    
The last command prints Protection activated and verified: [ADR-001] (rule installed). The Claude Code setup shows each step’s output. Commit the ADR and the memory file.


    
3. Register the hook

    
Save this script as write_codex_hooks.py and run it from the repository root with the same interpreter. It writes .codex/hooks.json with your interpreter and hook paths filled in, so you edit nothing by hand:

    

    
~/.mneme-venv/bin/python write_codex_hooks.py

    
The file it writes registers one command for three Codex events:

    
    
      
  • SessionStart records the state of the repository when the session begins.
    • 
      
  • PreToolUse on apply_patch checks the lines a patch adds and denies the call if they break an active rule.
    • 
      
  • Stop compares the repository with that starting state and checks each changed file whole.
    • 
    

    
This follows the hook template in Mneme’s Codex validation. We ran the script and the command it wrote against a test event; on Windows the paths come out with backslashes escaped as JSON requires.


    
4. Trust the hooks

    
Codex runs a hook only after you approve it. Start codex in the repository and type /hooks, the Codex command that lists configured hooks; review the three Mneme entries and trust them. Codex remembers one approval per event entry, so if the command changes later, for example after you rerun the script with another interpreter, trust it again.


    
5. Add the required CI check

    
Copy the GitHub Actions workflow or GitLab CI job and make it required. The CI check covers files changed outside a Codex session, which the hook never sees. Neither the hook nor CI stops a file from being deleted.

What gets blocked, and what doesn’t

    
    
      
  • Denied before they run: apply_patch Add File and Update File operations. In a patch with several operations, one violation denies the whole call.
    • 
      
  • Checked only at the end of the turn: shell and script writes. The file exists by then; the Stop check sends Codex back with the violation.
    • 
      
  • Not protected: deleting a file. A deletion adds no content, so the hook skips it; the Stop audit records it.
    • 
      
  • Files already modified before the session are ignored unless Codex touches them. Once it does, the whole file must pass at Stop, including violations that were there before.
    • 
      
  • Fails open, visibly: when the check can’t run, the patch goes through rather than being blocked. If the check can’t run, times out or can’t read a file, the hook adds an [mneme] UNEVALUATED note for Codex and does not block.
    • 
      
  • Not yet tested: changes made through Model Context Protocol (MCP) tools inside Codex.
    • 
    

    
The Codex CLI integration page links the validation evidence for each of these.

  


  

    
Troubleshooting

    
The hooks never run

    
They aren’t trusted, or a changed command lost its trust. Run /hooks again in Codex and trust all three.

    
Codex reports a hook error

    
The interpreter in hooks.json can’t import Mneme, or a path is wrong. Run the path command from step 1 with exactly that interpreter, and copy its output again.

    
A Celery patch goes through with no note

    
Two causes produce no output at all. The hook found no .mneme/project_memory.json in the session’s working directory, and with none it allows every patch silently; start Codex from the repository root. Or the rule isn’t active: mneme audit --memory .mneme/project_memory.json --repo-root . should list ADR-001 as protected, and if it says Mneme-ready, repeat step 2.

    
Codex shows a WARN note and applies the patch

    
MNEME_HOOK_MODE=warn is set in the environment Codex runs in. The hook then reports the violation without denying it:

    

    
Unset the variable to deny again.
