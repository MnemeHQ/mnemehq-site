Goal

Installing Mneme and protecting a decision are two separate steps, on purpose. mneme setup prepares a repository but never blocks anything. Enforcement starts only when you activate a rule for a specific decision. This guide takes one ADR from a fresh install to an active, verified rule.

Three terms come up throughout:

  • Memory file: .mneme/project_memory.json, where Mneme stores your compiled decisions and their rules.
  • Mneme-ready: the audit found a decision with a clear, checkable intent and a rule Mneme could install for it, but no rule is installed yet.
  • Protected: the audit observes enforcement for the decision. In this guide, that is an installed rule.

Prerequisites

  • Python 3.11 or newer, and pipx.
  • A git repository with a docs/adr/ directory.
  • No coding agent and no continuous integration (CI) setup. Later guides add both.

3. Run setup

    
From the repository root:

    
mneme setup

    

    
Setup creates the memory file and reports what it found, including the ADR it noticed. Enforcement: Not enabled is expected: setup never installs a rule, a hook or a CI check.


    
4. Preview, then apply the import

    
Without --apply, the import writes nothing. Here the preview exits with code 1 and warns that the ADR has no enforceable rule yet. That is expected: activation adds the rule later.

    
mneme adr import docs/adr --memory .mneme/project_memory.json

    

    
mneme adr import docs/adr --memory .mneme/project_memory.json --apply

    

  


  

    
Run

    
5. Audit the repository

    
mneme audit --memory .mneme/project_memory.json --repo-root .

    

    
ADR-001 is Mneme-ready, and the audit names the rule it would install: FORBID_LITERAL: celery.


    
6. List the activation candidates

    
mneme protect list --memory .mneme/project_memory.json

    

    
Read the applies to line before you go on. This rule applies to every file you check except ADR-001's own file and the memory file.


    
7. Validate the rule

    
Validation runs four checks on the proposed rule and changes nothing:

    
mneme protect validate ADR-001 --memory .mneme/project_memory.json

    


    
8. Activate it

    
mneme protect activate ADR-001 --memory .mneme/project_memory.json

    

    
Activation adds the rule to ADR-001's current version in the memory file, switches the project out of setup mode, then re-runs the audit's assessment for ADR-001 to confirm it is now Protected.

  


  

    
Expected result

    
The audit now counts ADR-001 as Protected:

    
mneme audit --memory .mneme/project_memory.json --repo-root .

Evidence

    
mneme protect status shows one decision's tier, its rule and whether the rule is installed. Nothing in it is stored separately; Mneme derives it from the memory file each time.

    
mneme protect status ADR-001 --memory .mneme/project_memory.json

    

    
Commit .mneme/project_memory.json with the ADR. The installed rule lives in that file. The agent hooks and CI checks in the next guides read it, so they enforce every rule installed in it.

  


  

    
Troubleshooting

    
The import stops with missing required field 'priority'

    
The import crashes with a Python traceback. The last line names the file and the missing field:

    

    
Add priority: foundational (or another priority) to the ADR's frontmatter and import again.


    
The audit says Requires modelling, and there are no candidates

    
The ADR's intent is clear to a person, but the title doesn't name a single banned term, so Mneme won't guess a rule. This ADR is titled "Request handlers must not import the database client":

    

    
Either retitle it in one of the shapes from step 2, or write the rule yourself in a ## Constraints section, as Guide 1 shows.


    
Already Protected when you activate again

    

    
Activation is idempotent. Running it twice never installs a second copy of the rule.


    
Re-importing an edited ADR is refused

    
After you edit an activated ADR and re-import it with --update-existing, the import stops with exit code 2:

    

    
The activated rule lives in the memory file, not in the ADR, so a new version of the ADR would drop it. Mneme refuses rather than switch protection off silently. Say what you want: --preserve-protection with the rule id from the message keeps the rule, and --release-protection drops it.

    
mneme adr import docs/adr --memory .mneme/project_memory.json --apply --update-existing --preserve-protection ADR-001:FORBID_LITERAL:9e170833e847f7b3c7143e0d2be5d4b7

    

    

  


  

    
Limits

    
    
      
  • The installed rule matches celery as a whole, case-sensitive token, in any file you check except ADR-001's own file and the memory file. It does not match Celery, CELERY or celery_app. A document or comment that mentions celery as a word fails too. To limit a rule to certain paths, write it yourself with include_paths, as in Guide 1.
    • 
      
  • Activation installs one rule for one decision. It doesn't start any agent hook or CI job. Until you add those, the rule runs only when you call mneme check.
    • 
      
  • The audit derives a rule only from the title shapes in step 2 or a single-term FORBID_DEPENDENCY constraint. It never invents a rule from free prose.
